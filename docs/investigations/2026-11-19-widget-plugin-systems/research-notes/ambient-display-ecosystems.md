# Ambient and household display ecosystems: third-party apps and phone configuration (prior art for Homeboard TV)

Research date: 2026‑11‑19. GitHub figures come from `gh api` calls made on that day. Each finding is labelled **CONFIRMED** (read on the official page, in the source repo or in the API response) or **UNVERIFIED** (search-engine snippet, forum post or competitor blog only). Products covered: TRMNL (and its BYOS servers), Tidbyt / Pixlet / Tronbyt, LaMetric, AWTRIX 3 and its successor AWTRIX NG, InkyPi, Inkycal, MagicMirror² (added), Anthias (added), DAKboard, Mango Display, Cozyla, Skylight, Hearth, Amazon Echo Show widgets, Google Nest Hub / Google Photos Ambient API, and Samsung TV Ambient Mode.

## How does a third party write a widget/app (language, markup, data contract, rendering on device vs server)?

### Takeaway
There are three models. **Server-rendered markup** (TRMNL: Liquid + HTML + a CSS framework, turned into an image on a server) and **sandboxed scripts rendered off-device** (Tidbyt/Tronbyt Pixlet: Starlark scripts producing WebP) both ship pixels to a thin device. **Push-a-JSON-payload** devices (LaMetric indicator apps, AWTRIX 3 custom apps, DAKboard Fetch blocks) let the third party own the data logic and send only a declarative frame. Only the newest designs run third-party code on the device itself (AWTRIX NG Berry scripts, InkyPi Python plugins, MagicMirror JS modules), and those are all local, self-hosted projects rather than cloud products.

### Cited Findings

#### TRMNL (e-ink dashboard, cloud + open BYOS servers)
- CONFIRMED: TRMNL has three plugin types: "native, which our team builds + maintains; private, which users build for themselves; community, which anyone can build for other users". Recipes let users share private plugins "without hosting user data on their own server". [TRMNL Help: Plugin recipes](https://help.trmnl.com/en/articles/10122094-plugin-recipes)
- CONFIRMED: Architecture: the device "wakes up and requests content from web server every n period". The server "responds with the latest pre-rendered image for that device (PNG for most models)" plus timing for the next refresh, and the device renders it and sleeps. [TRMNL docs: How it Works](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: Device contract `GET /api/display` with an `Access-Token` header returns `image_url`, `filename` (used as a cache key) and `refresh_rate` (seconds to sleep). [TRMNL docs (llms-full)](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: Private plugin markup uses Shopify's Liquid templating. The Markup Editor "has a tab per layout (Full, Half Horizontal, Half Vertical, Quadrant) plus a Shared tab whose markup is prepended to every layout". The recommended styling comes from the TRMNL Framework design system ("recommended, but not required"), and authors may add inline styles or third-party libraries such as Highcharts. [TRMNL docs (llms-full)](https://docs.trmnl.com/go/llms-full.txt); [TRMNL Help: Private Plugins](https://help.trmnl.com/en/articles/9510536-custom-plugins)
- CONFIRMED: Private plugin data strategies: **Polling** (TRMNL fetches one or more URLs, with headers and body, and each response becomes an `IDX_<n>` node in merge variables), **Webhook** (you POST merge variables: max 5&nbsp;KB, or 10&nbsp;KB with TRMNL+), **Static**, **Plugin Merge** (combine data from your other plugins), and **Async Polling** (your server answers 202 and calls back later). [TRMNL Help: Private Plugins](https://help.trmnl.com/en/articles/9510536-custom-plugins); [TRMNL docs: Webhooks / Async Polling](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: Webhook rate limit: 12 posts per hour (30 with TRMNL+), with a 429 above that. Webhook use needs a device with the paid "Developer edition" enabled, otherwise 403. [TRMNL docs: Webhooks](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: **Third-party public plugins** (the "community" type hosted by the developer) use a simplified OAuth2 install flow. TRMNL POSTs to the developer's `plugin_markup_url` with a Bearer token, form-encoded `trmnl[...]` metadata such as `trmnl[device][width]`. The server returns JSON with `markup`, `markup_half_horizontal`, `markup_half_vertical`, `markup_quadrant` and optional `merge_variables`, each rendered as Liquid. The developer declares a "Supported Refresh Interval" from every 15&nbsp;minutes to once a day. Building third-party plugins requires the Developer Edition upgrade. [TRMNL docs: Plugin Creation / Installation / Screen Generation](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: The TRMNL OG is "an 800x480 pixel e-ink display" at 1-bit or 2-bit. TRMNL X and BYOD screens "have their own sizes and bit depths -- the Framework adapts the same markup to each". Images must fit the model's `image_size_limit`: 90,000&nbsp;bytes for ESP32 boards without PSRAM, 750,000&nbsp;bytes for TRMNL X. [TRMNL docs (llms-full)](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED: `trmnlp` is a local dev server that watches Liquid templates. A project is `src/full.liquid`, `src/half_horizontal.liquid`, `src/half_vertical.liquid`, `src/quadrant.liquid`, `src/shared.liquid` and `src/settings.yml`, and `push` sends it to the TRMNL server. [usetrmnl/trmnlp README](https://github.com/usetrmnl/trmnlp)
- CONFIRMED: TRMNL also publishes a CLI of about 140 commands, generated from its OpenAPI document, and an MCP server for AI agents. [TRMNL docs: CLI](https://docs.trmnl.com/go/llms-full.txt)

#### Tidbyt / Pixlet and Tronbyt (64×32 LED matrix)
- CONFIRMED: Pixlet apps are written in Starlark, "a simple, Python-like language". Scripts "retrieve data over HTTP, transform it and use a collection of Widgets". The Pixlet CLI "renders the result as a WebP or GIF animation", which can be served in a browser or pushed to a device with `pixlet push`. [tidbyt/pixlet README](https://github.com/tidbyt/pixlet); [tronbyt/pixlet README](https://github.com/tronbyt/pixlet)
- CONFIRMED: Entry point `main(config)` returns `render.Root(child=...)`, for example `render.Text("Hello, World!")`. [Pixlet schema doc](https://github.com/tidbyt/pixlet/blob/main/docs/schema/schema.md)
- CONFIRMED: Tidbyt's stock firmware "routes all of its requests through the Tidbyt company's servers". The open HDK firmware "downloads a WebP image from a URL" and displays it. Rendering is off-device. [Tom MacWright, "Tidbyt without the company" (2025‑04‑12)](https://macwright.com/2025/04/12/tidbyt-second-life)
- CONFIRMED: The Tronbyt Server client contract is to "pull WebP images from the `/next` endpoint and loop the animation for the duration specified in the `Tronbyt-Dwell-Secs` response header", with an optional `Tronbyt-Brightness` header (0–100). [tronbyt/server README](https://github.com/tronbyt/server)

#### LaMetric Time / Sky
- CONFIRMED: An **indicator app** displays "icons, numbers, text and charts that must stay on the device at all times". Data arrives by **Local Push** (sent in the local network, delivered at once) or **Poll** (the app polls a URL at a set interval, used "when data … changes often, requires authentication or additional user parameters"). The payload is JSON frames, for example `{"frames":[{"icon":3219,"text":"2"}]}`. [LaMetric docs: First Indicator App](https://lametric-documentation.readthedocs.io/en/latest/guides/first-steps/first-lametric-indicator-app.html)
- UNVERIFIED: LaMetric offers three app types to developers: Indicator, Button and Notification. [search snippet of LaMetric docs/help](https://lametric-documentation.readthedocs.io/en/latest/guides/first-steps/first-lametric-indicator-app.html); [LaMetric Help: Indicator app](https://help.lametric.com/support/solutions/articles/6000011972-indicator-app)
- CONFIRMED: The device's local API names app instances "widgets": "Device can run multiple instances of an app. These instances are called widgets." Apps declare `actions` with typed parameters (`data_type` bool/int/string, `format` regexp, `required`). [LaMetric docs: Device Apps API](https://lametric-documentation.readthedocs.io/en/latest/reference-docs/device-apps.html)

#### AWTRIX 3 (Ulanzi TC001 pixel clock) and AWTRIX NG
- CONFIRMED: AWTRIX 3 custom apps are pushed from outside, by MQTT topic `[PREFIX]/custom/[appname]` or an HTTP `POST` to `/api/custom?name=[appname]` on the device's own IP address. The JSON keys are all optional: `text`, `icon`, drawing instructions (`draw` array), `lifetime` (remove the app if not updated within N&nbsp;seconds; `lifetimeMode` 1 marks it stale with a red frame instead), and others. Notifications go to `/api/notify`. [awtrix3 docs/api.md](https://github.com/Blueforcer/awtrix3/blob/main/docs/api.md)
- CONFIRMED: AWTRIX 3 is "meant to be a companion for your smarthome like HomeAssistant, IOBroker, FHEM, NodeRed". [awtrix3 README](https://github.com/Blueforcer/awtrix3)
- CONFIRMED: **AWTRIX 3 is discontinued.** "Development of AWTRIX 3 has ended … no further releases". Its successor AWTRIX NG adds "Apps that run on the device — Berry scripts edited in the browser, with HTTP, MQTT and Modbus TCP". The commit marking the archive is dated 2026‑08‑07. [awtrix3 README](https://github.com/Blueforcer/awtrix3); [awtrix3 commits](https://github.com/Blueforcer/awtrix3/commits/main)
- CONFIRMED: AWTRIX NG scripts "are small programs in Berry, written and saved in the web UI. They fetch data from the internet, talk MQTT and Modbus, keep their state across restarts and have settings of their own. A script with an error shows a red frame, and everything else keeps running." [awtrix-ng README](https://github.com/Blueforcer/awtrix-ng)

#### InkyPi (Raspberry Pi e-ink)
- CONFIRMED: A plugin is a directory under `src/plugins/<id>/` holding a Python class that subclasses `BasePlugin` and implements `generate_image(settings, device_config)`. It returns a `PIL.Image` and raises `RuntimeError` with a message for the web UI. Images can be drawn with Pillow or produced by `render_image(dimensions, html_file, css_file, template_params)` from Jinja HTML/CSS templates that extend `plugin.html`. The plugin also carries `plugin-info.json` (display_name, id) and `icon.png`. [InkyPi: Building plugins](https://github.com/fatihak/InkyPi/blob/main/docs/building_plugins.md)
- CONFIRMED: There are 20 bundled plugins (ai_image, ai_text, apod, calendar, clock, comic, countdown, github, image_album, image_folder, image_upload, image_url, newspaper, rss, screenshot, todo_list, unsplash, weather, wpotd, year_progress). [InkyPi src/plugins](https://github.com/fatihak/InkyPi/tree/main/src/plugins)

#### Inkycal
- CONFIRMED: Inkycal is "a small dashboard for e-paper screens" on a Raspberry Pi with "Custom Python modules". Its modules directory holds 16 modules (agenda, calendar, feeds, fullweather, image, jokes, server, slideshow, stocks, textfile, tindie, todoist, weather, webshot, xkcd, plus a dev module) and a `template.py`. [Inkycal README](https://github.com/aceinnolab/Inkycal); [Inkycal modules](https://github.com/aceinnolab/Inkycal/tree/main/inkycal/modules)

#### MagicMirror² (added: the largest open household-display module ecosystem)
- CONFIRMED: Third parties write "modules", recommended to be named `MMM-…`, starting from the MMM-Template. Module READMEs are asked to include a screenshot, a one-line description and the external APIs used. [MagicMirror docs: Module development](https://docs.magicmirror.builders/module-development/introduction.html)

#### DAKboard (benchmark, brief)
- CONFIRMED: Third-party data enters through an "External Data/Fetch" block in a Custom Screen. It takes a URL returning plain text, a JSON object of name–value pairs or a JSON array (a `value` field is required; `title` and `subtitle` are optional). Authentication options are None, Basic, Bearer Token or Custom Header, and the block has Formatting, Rules and Schedule tabs. There is no code-level plugin. [DAKboard: External data fetch](https://dakboard.freshdesk.com/support/solutions/articles/35000062047-external-data-fetch-formatting-options)

#### Amazon Echo Show widgets
- CONFIRMED: "An Alexa widget displays quick, essential information related to a skill and lets users perform quick actions". Widgets belong to an Alexa skill and are built with APL (Alexa Presentation Language) packages. [Amazon: About Widgets and APL](https://developer.amazon.com/en-US/docs/alexa/alexa-presentation-language/about-widgets-and-apl.html)
- UNVERIFIED (search summary of the same page): the widget reads from an on-device data store that the skill refreshes through the Data Store REST API; `Alexa.DataStore.PackageManager` tells the skill when a package is installed, removed or updated; buttons send `SendEvent` to the skill. [Amazon: About Widgets and APL](https://developer.amazon.com/en-US/docs/alexa/alexa-presentation-language/about-widgets-and-apl.html)

#### Google Nest Hub / Google Photos Ambient API; Samsung TV Ambient Mode
- CONFIRMED: Google exposes a **Google Photos Ambient API** that lets developers "integrate Google Photos into slideshow experiences on smart TVs and photo frames". It uses "OAuth 2.0 for TV and Limited-Input Device Applications". This is a content API, not a widget model. [Google: About the Photos Ambient API](https://developers.google.com/photos/ambient/guides/about?hl=en)
- UNVERIFIED: The Nest Hub Photo Frame once had an "Experimental" Facebook/Flickr source that was later removed. Google Photos restricted third-party frame access in March 2025, and Aura frames regained sync through the Ambient API in June 2026. [9to5Google (2026‑06‑04)](https://9to5google.com/2026/06/04/google-photos-support-has-returned-for-auras-digital-photo-frames/); [9to5Google (2025‑03‑05)](https://9to5google.com/2025/03/05/google-photos-digital-frames/)
- UNVERIFIED: No public SDK for third-party apps in the Samsung TV "Ambient" section was found. A Samsung developer-forum question about it went unanswered by Samsung staff. [Samsung Developer Forum: Developing Ambient mode](https://forum.developer.samsung.com/t/developing-ambient-mode/28315)

### Inferences
- Every cloud product (TRMNL, Tidbyt, LaMetric poll apps, DAKboard Fetch) keeps third-party code **off the display device**. The display gets an image (TRMNL, Tidbyt) or a declarative payload (LaMetric, AWTRIX 3, DAKboard). This is the safety boundary that lets them accept untrusted contributions.
- TRMNL's "one template per layout size" (full / half_horizontal / half_vertical / quadrant) is the closest analogue to Homeboard's compact tile versus expanded view and its Small/Medium/Large presets. It makes the author design each size explicitly instead of relying on responsive CSS.
- LaMetric's naming of app instances as "widgets", each with typed action parameters, matches Homeboard's widget-kind versus widget-instance split.
- AWTRIX's move from "external system pushes JSON" (v3) to "scripts run on the device, edited in a browser" (NG) is a recent (2026) data point that hobbyist users want on-device apps once the device has a web UI.

### Gaps
- LaMetric "native apps" and the LaMetric Sky app model: the LaMetric overview and how-it-works pages returned no content when fetched, and no official page describing native app development was found.
- Tidbyt's exact server-side render cadence for installed apps and its rotation/dwell defaults on the official cloud were not found in public docs; only the Tronbyt `Tronbyt-Dwell-Secs` contract is confirmed.
- No public developer SDK or third-party widget API was found for Skylight, Hearth, Mango Display or Cozyla. Cozyla instead runs ordinary Android apps (see next section).

## How is configuration expressed (declared schema → generated phone form, or free HTML settings page?) and where is it stored?

### Takeaway
The products split cleanly. **Declared-schema → generated form**: TRMNL custom-fields YAML, Pixlet `get_schema()`, LaMetric typed parameters. **Free HTML settings page**: InkyPi `settings.html`. **Config file**: MagicMirror `config.js`, Inkycal `settings.json` (with a web generator). Storage follows the business model: cloud accounts (TRMNL, Tidbyt, LaMetric, Mango, DAKboard) versus local SQLite or files (Tronbyt, BYOS servers, InkyPi, MagicMirror).

### Cited Findings
- CONFIRMED (TRMNL): plugin settings are a YAML list of custom fields: "Create user-facing configuration fields with YAML". Supported `field_type`s are `author_bio, url, string, multi_string, text, code, number, password, date, time, select, xhrSelect (single or multi), xhrSelectSearch, plugin_instance_select, time_zone, copyable, copyable_webhook_url, boolean, lat_lon`, and "Where possible, TRMNL follows HTML5 input types". [TRMNL Help: Custom plugin form builder](https://help.trmnl.com/en/articles/10513740-custom-plugin-form-builder)
- CONFIRMED (TRMNL): common field keys are `keyname`, `field_type`, `name`, `description`, `description-LOCALE` (per-locale labels), `help_text`, `optional`, `default`, and `group` (accordion grouping). `conditional_validation` with `when:` / `hidden:` shows or hides fields. TRMNL's own Private Plugin editor uses that to switch fields by Strategy (Polling / Webhook / Static). [TRMNL Help: Custom plugin form builder](https://help.trmnl.com/en/articles/10513740-custom-plugin-form-builder)
- CONFIRMED (TRMNL): form values interpolate into Polling URLs, headers and bodies as `{{ api_key }}`, and global variables such as `{{ trmnl.user.first_name }}` are available too. [TRMNL Help: Private Plugins](https://help.trmnl.com/en/articles/9510536-custom-plugins)
- UNVERIFIED (TRMNL): invalid YAML "will be ignored and no errors will be returned", and TRMNL offers a visual form builder that generates the YAML. [search summary of TRMNL Help: form builder](https://help.usetrmnl.com/en/articles/10513740-custom-plugin-form-builder)
- CONFIRMED (TRMNL): the public recipes API returns each recipe's `custom_fields` as JSON (for example `keyname: user_location, field_type: string, required: true`, or a `select` with options Fahrenheit/Celsius). [TRMNL docs: Recipes API](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED (TRMNL): configuration lives in the TRMNL cloud account, managed through an Account API with scoped key capabilities (`read`, `content`, `devices`, `delete`, `profile`, `apps`). [TRMNL docs: More Endpoints](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED (Pixlet/Tidbyt): "Schema provides structure for configuring apps. We use schema inside of the Tidbyt mobile app … and store the values inside of our database. … we call `get_schema()`. When a user saves the installation, we store the results in our database. Every time we render the app, we pass the values into the `config`". [Pixlet schema doc](https://github.com/tidbyt/pixlet/blob/main/docs/schema/schema.md)
- CONFIRMED (Pixlet): schema field kinds are Color, Datetime, Dropdown, Generated, Location, LocationBased, OAuth2, PhotoSelect, Text, Toggle, Typeahead, plus "Dynamic Fields" and Icons. [Pixlet schema doc](https://github.com/tidbyt/pixlet/blob/main/docs/schema/schema.md)
- CONFIRMED (Tronbyt): there is no mobile app. Configuration happens in the server's local web UI ("Add and configure an app via the built-in Pixlet interface. Save to see the app preview."), stored in a local database (`tronbyt.db`, migrated from `usersdb.sqlite`). Drawbacks include "the lack of a mobile app" and "limited support for … apps relying on Tidbyt's cloud services for secrets". [tronbyt/server README](https://github.com/tronbyt/server)
- CONFIRMED (LaMetric): app action parameters declare `data_type`, `name`, `format` (regexp) and `required`. [LaMetric Device Apps API](https://lametric-documentation.readthedocs.io/en/latest/reference-docs/device-apps.html)
- UNVERIFIED (LaMetric): options a developer adds to a poll app appear to users like built-in app settings, and "are sent with each GET request to your server in form of query parameters". [LaMetric support forum](https://help.lametric.com/support/discussions/topics/6000017895)
- CONFIRMED (InkyPi): settings are a **free-form HTML** file. "create a `settings.html` file … The `name` attribute of each input element will be passed as keys in the `settings` argument of the `generate_image` function." `generate_settings_template()` can inject template variables, for example to fill dropdowns, and editing a playlist instance "should prepopulate the form with the current settings". [InkyPi: Building plugins](https://github.com/fatihak/InkyPi/blob/main/docs/building_plugins.md)
- CONFIRMED (InkyPi): "Web Interface allows you to update and configure the display from any device on your network." [InkyPi README](https://github.com/fatihak/InkyPi)
- CONFIRMED (Inkycal): users "Create `settings.json` in the Web UI" generator hosted at inkycal.aceinnolab.com/ui, then install it on the Pi. The README also lists a "Local web UI". [Inkycal README](https://github.com/aceinnolab/Inkycal)
- CONFIRMED (MagicMirror²): configuration is a `config.js` file. Each module entry has `module`, `position`, `header`, `classes`, `hiddenOnStartup`, `disabled`, `configDeepMerge` and a module-specific `config` object merged with module defaults. [MagicMirror docs: Module configuration](https://docs.magicmirror.builders/modules/configuration.html)
- CONFIRMED (AWTRIX NG): scripts "have settings of their own" and are edited in "A full web UI on the device". [awtrix-ng README](https://github.com/Blueforcer/awtrix-ng); [awtrix3 README](https://github.com/Blueforcer/awtrix3)
- CONFIRMED (DAKboard): block configuration (URL, auth, formatting rules, schedule) is set in the DAKboard web options under "Custom Screen Settings", tied to a cloud account. [DAKboard: External data fetch](https://dakboard.freshdesk.com/support/solutions/articles/35000062047-external-data-fetch-formatting-options)

### Inferences
- TRMNL's YAML and Pixlet's `get_schema()` are both "declare fields, let the platform render the form". This is what lets a phone-side form (TRMNL's web UI, Tidbyt's mobile app) configure code the platform did not write. Homeboard's phone-browser draft editor could render such a declared schema directly. TRMNL's `field_type` list and its `conditional_validation` are a ready vocabulary, and TRMNL's `description-LOCALE` keys show one way to carry Thai and English labels.
- InkyPi's free `settings.html` is the cheapest to implement but gives up validation, consistent styling and any non-browser rendering (for example on a TV remote UI). InkyPi has to ask authors to "visually match" the existing UI.
- Values that are secrets (TRMNL `password` fields, Tidbyt OAuth2 fields) are the hard part of local-only storage. Tronbyt explicitly lost apps that depended on Tidbyt cloud-held secrets.

### Gaps
- TRMNL's exact settings variable path in Liquid (search snippet: `trmnl.plugin_settings.custom_fields_values`) was not confirmed on a page read in full.
- How the Tidbyt mobile app renders Pixlet `Generated` and `Typeahead` fields at runtime (server callbacks) was not traced.
- The contents of Inkycal's "Local web UI" (the README line was truncated in the fetch) were not confirmed.

## How are screens composed: fixed layouts, free grid, playlists/rotation, time-of-day schedules?

### Takeaway
Small and e-ink devices use **one app per screen in a rotation** (Tidbyt/Tronbyt, LaMetric, AWTRIX). TRMNL adds **fixed mashup layouts** (full, half/half, quadrant, and "fluid" layouts on larger screens) inside **drag-ordered playlists** with item scheduling. InkyPi uses **time-scheduled playlists**. **Free grids** belong to the family-calendar and dashboard products (DAKboard blocks, Cozyla and Mango drag-and-drop widgets) and to MagicMirror's **named regions**.

### Cited Findings
- CONFIRMED (TRMNL): "At TRMNL we use a Playlists table to manage the ordering of plugin instances, letting users drag/drop different items in whatever sequence they prefer." [TRMNL docs: Display API / Other infrastructure](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED (TRMNL): mashups combine connected plugins in a layout chosen from the Playlists tab ("50/50 split screen", Section A / Section B). Devices with 10.3" screens (TRMNL X, reMarkable, E1003) get extra "Fluid Mashups". Plugins inside a mashup keep refreshing even when their full-screen item is removed from the playlist. [TRMNL Help: Mashups](https://help.trmnl.com/en/articles/10168132-mashups)
- CONFIRMED (TRMNL): "If they connected your plugin as part of a left/right Mashup, TRMNL will look for HTML inside the `markup_half_vertical` node … A layout you leave out renders as 'view not available'." Public marketplace plugins "must provide HTML for all available markup layouts". [TRMNL docs: Plugin Screen Generation](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED (TRMNL): playlists support "Playlist item visibility and scheduling". This is listed among the TRMNL features that do not carry over to Tidbyt hardware. [TRMNL Help: Tidbyt](https://help.trmnl.com/en/articles/12430929-tidbyt)
- CONFIRMED (TRMNL): "only plugins on a Playlist (or inside a Mashup) will sync fresh data". A hidden plugin still refreshes if a Plugin Merge plugin reads from it. [TRMNL docs (llms-full)](https://docs.trmnl.com/go/llms-full.txt)
- CONFIRMED (LaraPaper BYOS): supports schedule-based hybrid use, "update your custom Train Monitor every 5 minutes in the morning, while displaying native TRMNL plugins throughout the day". [usetrmnl/larapaper README](https://github.com/usetrmnl/larapaper)
- CONFIRMED (Tronbyt): rotation is server-driven. Each `/next` response carries `Tronbyt-Dwell-Secs`. [tronbyt/server README](https://github.com/tronbyt/server)
- CONFIRMED (AWTRIX 3): apps form a "loop" (`/api/loop` lists all apps in the loop). There are endpoints to switch to the next, previous or a specific app, plus stacking notifications that interrupt the loop. [awtrix3 docs/api.md](https://github.com/Blueforcer/awtrix3/blob/main/docs/api.md)
- CONFIRMED (LaMetric): `PUT /api/v2/device/apps/next|prev` and `.../widgets/:id/activate` switch between app instances. Each widget has an `index` (position) and, since API 2.3.0, a `visible` flag. [LaMetric Device Apps API](https://lametric-documentation.readthedocs.io/en/latest/reference-docs/device-apps.html)
- CONFIRMED (InkyPi): "Set up scheduled playlists to display different plugins at designated times". [InkyPi README](https://github.com/fatihak/InkyPi)
- CONFIRMED (MagicMirror²): the fixed named regions are `top_bar, top_left, top_center, top_right, upper_third, middle_center, lower_third, bottom_left, bottom_center, bottom_right, bottom_bar, fullscreen_above, fullscreen_below`. "Multiple modules with the same position will be ordered based on the order in the configuration file". [MagicMirror docs: Module configuration](https://docs.magicmirror.builders/modules/configuration.html)
- CONFIRMED (DAKboard): blocks are added to a Custom Screen and can be resized and moved freely. The Fetch block also has a Schedule tab. [DAKboard: External data fetch](https://dakboard.freshdesk.com/support/solutions/articles/35000062047-external-data-fetch-formatting-options)
- CONFIRMED (Cozyla): "Customizable Dashboard – Drag, drop, and resize widgets", and "personalized dashboards for every family member". [Cozyla Calendar+ product page](https://www.cozyla.com/products/digital-family-calendar-all-in-one-smart-touchscreen)
- UNVERIFIED (Mango Display): users "drag and drop widgets wherever they want them" with Google Photos or Apple Photos backgrounds (vendor's own comparison blog). [Mango Display: Skylight alternatives](https://mangodisplay.com/best-skylight-calendar-alternatives/)

### Inferences
- Homeboard's model (a paged grid with spans and size presets) sits between TRMNL's fixed mashups and DAKboard/Cozyla's free grids. TRMNL shows that a small closed set of slot shapes is what makes third-party templates feasible, because authors design each shape. A free grid pushes responsive-layout work onto every widget author.
- TRMNL's "only items on a playlist refresh" rule is a useful scheduling and cost rule for any widget host: fetch data only for widgets that can be seen.
- LaMetric's per-instance `index` and `visible` flags and TRMNL's per-item visibility map directly onto a JSON layout document like Homeboard's.

### Gaps
- TRMNL's playlist time-window scheduling UI (exact fields, for example a time range per item) was not read on an official page; it is only confirmed to exist.
- Skylight's and Hearth's home-screen composition (fixed versus configurable) has no official public documentation that was found.

## Distribution: marketplace/catalogue, review, private vs public apps, forking/remixing ("recipes"), versioning

### Takeaway
TRMNL has the richest model: private → unlisted (shareable link, no moderation) → public recipe (human plus AI review), with **install = linked and auto-updated** versus **fork = editable copy without updates**. Tidbyt/Tronbyt use a **GitHub monorepo with PR review and a linter** (`pixlet check`). LaMetric uses a developer portal with a publish step and email confirmation. The open-source e-ink projects mostly have no catalogue: plugins live in the main repo or in community-curated lists.

### Inferences
- Licence compatibility with Homeboard's MIT licence (general licensing reasoning, not legal advice):
    - MIT sources (TRMNL Framework code, Terminus, LaraPaper, trmnlp, trmnl-android, MagicMirror core) can be reused freely with notice retention. The TRMNL fonts are OFL 1.1, which allows bundling with attribution, but BlockKie under CC BY 3.0 needs attribution.
    - Apache-2.0 sources (Pixlet, tidbyt/community apps, Tronbyt) can be included in an MIT-licensed distribution if the Apache NOTICE and licence text are kept and changes are marked. They cannot be relicensed as MIT.
    - GPL-3.0 sources (TRMNL firmware, InkyPi, Inkycal) cannot be copied into Homeboard without making the combined work GPL-3.0. Talking to them over a network protocol does not trigger that.
    - AWTRIX 3 (CC BY-NC-SA 4.0) and AWTRIX NG (PolyForm Noncommercial) forbid commercial use, so their code is not MIT-compatible. Only their public API shape is safe reference material.
- The two healthiest open ecosystems by recent activity are TRMNL's (firmware, Terminus and LaraPaper all pushed on 2026‑11‑19, LaraPaper releasing weekly) and Tronbyt (server and pixlet releases on 2026‑11‑13). The original Tidbyt Pixlet has had no release since 2024‑09‑30.

## Could Homeboard host apps from these ecosystems, and which products configure a big screen from a phone the way Homeboard does?

### Takeaway
Two ecosystems are technically and legally hostable. **Pixlet/Tronbyt** (Apache-2.0, about 1,100 apps, pixel-art output at 64×32 or 128×64) could be hosted by acting as a Tronbyt client or by embedding Pixlet. **TRMNL recipes** (Liquid + MIT framework CSS; about 1,280 public recipes on trmnl.com plus about 170 in an OSS catalogue) could be hosted by rendering Liquid into a WebView, or by acting as a BYOS/trmnl-android-style image client. Both were designed for e-ink or LED canvases, not a 16:9 colour TV, and TRMNL's recipe markup needs an authenticated TRMNL API. For phone configuration, the closest analogues are device-code pairing through a vendor cloud (Mango Display, Google's TV OAuth flow) and **local web UIs** (Tronbyt, InkyPi, AWTRIX NG, BYOS servers). No product found pairs a phone to a TV through a QR code and a temporary local server with transactional Apply/Undo, which is Homeboard's model.

### Cited Findings
- CONFIRMED (Tronbyt as a host contract): "Developing additional clients for Tronbyt Server is straightforward: pull WebP images from the `/next` endpoint and loop the animation for the duration specified in the `Tronbyt-Dwell-Secs` response header." [tronbyt/server README](https://github.com/tronbyt/server)
- CONFIRMED (Pixlet output targets): Pixlet apps "can be served in a browser, rendered as WebP or GIF animations, or pushed to a physical Tronbyt device". ### Inferences
- **Pixlet on Homeboard.** Three routes. (1) Have Homeboard speak the Tronbyt client contract against a LAN Tronbyt server: lowest effort, but it adds a second box or container to a household with no server. (2) Embed Pixlet (Go) through gomobile or a sidecar binary on Android: large native dependency, Apache NOTICE obligations. (3) Re-implement Starlark plus render widgets in Java: very large. In every case the output is pixel art meant for 64×32 or 128×64. On a TV it would suit a tile-sized "retro LED" widget, not full-screen content. Pixlet's `get_schema()` JSON could drive Homeboard's phone form directly. Apps that rely on Tidbyt OAuth2 or cloud-held secrets would not work locally, as Tronbyt already found.
- **TRMNL recipes on Homeboard.** Homeboard could render Liquid templates in an Android WebView with the MIT TRMNL Framework CSS. The four layout templates map onto Homeboard tile sizes. The `settings.yml` / custom-fields YAML maps onto a phone form, and polling URLs with `{{ keyname }}` interpolation map onto a local fetcher. Obstacles: (a) trmnl.com recipe markup needs an authenticated TRMNL API key, which conflicts with Homeboard's no-accounts stance. The OSS trmnlp-compatible catalogue, with per-repo licences, avoids that. (b) Recipes were designed for 1–2-bit greyscale e-ink at 800×480, so they would look stark on a colour TV unless restyled. (c) Recipe licences are unstated, so redistributing them in a Homeboard catalogue is not clearly permitted. Fetching them on the user's behalf, as LaraPaper does, is the precedent. A Java Liquid engine would be needed; whether a suitable MIT/Apache one exists was not checked here.
- **Image-client route.** Homeboard could act as a TRMNL/BYOS display (as trmnl-android does) or a Tronbyt display, showing a server-rendered PNG or WebP in a widget slot. That inherits the whole catalogue at the cost of depending on a TRMNL account or a self-hosted server.
- **Not hostable:** AWTRIX 3 and NG apps (non-commercial licences; their "apps" are JSON pushed by home-automation systems or Berry scripts tied to the firmware), InkyPi and Inkycal plugins (GPL-3.0 Python with Pillow/Jinja on a Pi; licence-incompatible if bundled), MagicMirror modules (JS/DOM plus Node `node_helper`; would need a browser and Node runtime on the TV; licences vary per module), and Echo Show widgets, Skylight, Hearth and Cozyla (closed platforms; Cozyla's "apps" are ordinary Play Store apps).
- **Phone-configuration prior art.** Mango Display's device-code-plus-cloud-login flow is the commercial norm. Tronbyt, InkyPi, AWTRIX NG and the BYOS servers show the local-web-UI norm in open source, but they are always-on servers, not a temporary server summoned by a QR code. No product found offers transactional Apply/Undo of a draft layout. TRMNL's pre-render preview ("refresh your Playlists tab to see the preview image") and Tronbyt's "Save to see the app preview" are the nearest equivalents to a draft preview.

- Whether TRMNL's Terms of Service allow a third-party client to fetch and render recipe markup through a user's API key was not checked. LaraPaper does it, but that is not proof of permission.
- No product was found that pairs a phone to a TV through a QR code pointing at a temporary LAN server. Chromecast, YouTube "link with TV code" and Fully Kiosk Browser remote admin were not researched in this pass and may be closer analogues.
- Feasibility of running Pixlet on Android/ARM (gomobile or a static binary) was not tested.
- The availability and licence of a Java Liquid engine (for example liqp) were not verified.
