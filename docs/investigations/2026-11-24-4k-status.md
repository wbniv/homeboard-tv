# 4K tester and dashboard status

24 November 2026 · Updated 26 November

**The standalone resolution tester is implemented, and the actual dashboard now renders at 3840 × 2160 in a separate engineering app. Automatic native rendering in the normal launcher is still pending.** The separate resolution tester remains available for checking detail on the new TVs. The LG is already known to be 4K; its panel capability is settled and does not need another investigation.

## What works today

Dashboard scale now provides roughly four times the widget workspace at 50%
(8×4 → 16×8). Cast2 passed native preview, Cancel, Save/Undo and Rain, Calendar,
Air and Favorites full-screen Back/Restore. The separate native 4K package also
passed real Android provider-fixture rendering, move/resize into the extra space,
expansion and same-binding Remove/Undo. Original layout, focus and binding
permission were restored; zero test widget IDs remain. Phone browser UI and
Android editor protocol passed separately. See the
[26 November acceptance and screenshots](../testing/2026-11-26-dashboard-scale-acceptance.md).

Remaining: external phone-browser transport, broader provider compatibility,
accessibility/readability, lifecycle/output recovery, independent pixel delivery
and performance acceptance. Automatic native rendering in the ordinary launcher
is still pending; FPS work belongs to the separate measurement task.

## What the experiments established

The [surface log](../testing/2026-11-23-native-4k/cast2-surface/logcat.txt) records `logical=1920x1080`, `mode=3840x2160` and `surface=3840x2160 canvas=3840x2160 hardware=true`. Allocation and drawing at 4K succeeded despite the lower ordinary UI resolution.

The [View experiment log](../testing/2026-11-23-native-4k/cast2-views/logcat.txt) records a 3840 × 2160 presentation and a 3520 × 296 clock widget. Its original remote test failed to activate the intended button, so that run did not pass focus navigation. Later tester source changes explicitly forward focus movement and the Cast1 mode-list check passed; the updated behavior still needs 4K-device acceptance.

During the earlier coloured-background stripe test, Will saw grey with darkish pink stripes in the one-pixel band. That observation does not identify the cause. The current tester has true black/white patterns in both orientations to make the follow-up more useful. A 4K buffer or a resized screenshot alone cannot establish that individual pixels reach the panel correctly.

## Pending work in order

### 1 Verify the new TVs with the standalone tester

This is the immediate task. Record each tested TV and source separately, open the existing tester, and record requested mode, accepted output, surface dimensions and visible stripe detail. Compare the horizontal and vertical 1-, 2- and 4-pixel bands with direct panel observation or suitable close photographs. Record relevant TV processing and output format with the result. Keep the known LG available as a reference, rather than reopening its panel specification.

Acceptance should answer both “does this TV resolve native 4K detail?” and “does this source and rendering path deliver that detail?” Keep an inconclusive result explicit where scaling or processing prevents a clear answer.

### 2 Finish tester device acceptance

- Verify the current tester's 4K patterns, resolution backgrounds, remote focus, supported-mode scrolling and Back/exit restoration on a 4K source.
- Verify the Pixel orientation correction; 0.1.127 had a landscape activity with a portrait virtual display. The correction was implemented and installed, but the plan still leaves physical acceptance open.
- Exercise an accepted mode change and a rejected preference, buffer recreation, pause/resume, allocation failure and cleanup. The requested mode must remain distinct from the actual mode.

These are primarily verification tasks for existing code, not requests to rebuild the tester from scratch.

### 3 Prove a renderer for the actual dashboard

The real Home/All Apps hierarchy and native overlays now run in the separate
embedded-surface proof. D-pad focus, the four built-in dashboard expansions,
Back/Restore and the real Android provider fixture have passed the checks linked
above. Finish broader provider compatibility, touch/accessibility, animations,
video and lifecycle/output acceptance. Measure input latency, frame timing and
memory; the current functional passes do not close those gates.

### 4 Implement automatic selection and recovery

After renderer acceptance, select native 4K automatically on supported devices and preserve the working dashboard elsewhere. Handle allocation failure, surface loss, display changes and lifecycle recovery. Preserve saved layout and settings; avoid global display-size or density changes.

### 5 Raise asset resolution and validate the complete product

Lift the provider-image 1080p target only for the verified rendering path, with memory bounds. Verify static images, animation and actual video output separately. Finish 4K interaction acceptance, 1080p regression, Thai and larger text, wallpaper, screensaver, idle behavior, Back and Undo. Use the normal numbered deployment and coordinator workflow.

## Actual dashboard implementation on 25 November

The separate **Homeboard 4K Dashboard Test** now runs the actual production Java
hierarchy at native dimensions, with native modal overlays. Cast2 measurements
report `dashboard=3840x2160 surface=3840x2160 hardware=true`, density 640. Reviewed
checks cover Rain expansion, Back, the visible Restore dashboard action, All Apps
and World clock. Cast1 passed the 1920 × 1080 control with the same navigation
script. A separate process-kill check returned to the 4K dashboard after a cold
start. See the [verification record and captures](../testing/2026-11-25-native-4k-dashboard.md).

A private secondary Activity was rejected by Cast2's platform capabilities. Both
the Presentation and direct embedded-surface candidates then rendered the real
Views. The direct candidate embeds through SurfaceControlViewHost and keeps
expanded/editor content in the same hierarchy, rather than placing an oversized
physical-window Dialog over it. The normal launcher still uses its existing
windows; the proof package has independent settings.

Performance has not passed: the Presentation sample had a 105.56 ms median frame
completion, while the ordinary dashboard baseline also had late frames at
84.57 ms. The collector did not expose individual windowless rows for the direct
embedded root, and its process aggregates still show slow frames. No speedup is
claimed. Finish performance attribution, physical detail, remaining widgets and
providers, accessibility, video/wallpaper and mode/memory recovery before enabling
automatic 4K in ordinary Homeboard. The provider-image 1080p target remains.

Latest proof **0.1.149** is installed with matching APK hashes on Cast1, Cast2 and
the Pixel; the tablet install remains queued while unreachable. Its purple icon
and label **Homeboard 4K Dashboard Test** identify the separate app. Cast2's final
149 rendering check passed; the coordinator's automatic launcher-artwork checks
hit a plugin error, documented separately in the verification record.
